# Room AI shared and personal context

Objective: keep one public Room conversation while the AI learns each collaborator's closed teaching profile from that collaborator's public interactions; keep the profile hidden and browser-local, support conversational correction, and preserve Issue #22 voice behavior.
Branch: `feat/22-room-voice-questions`; delivery: ask-on-risk, local-only until the user separately authorizes delivery. Test runners: pnpm/Vitest and uv/Pytest.

## Specs

### S1 — Issue #18: Build request-time context

- User requirement: “esas dos memorias deberian estar en el modo global, imagina esto, estas en un salon de clase, la IA es como el profesor hablando con sus estudiantes (colaboradores), lo que pasa es lo siquiente, el profesor sabe el contexto de la clase, cada alumno le hace una pregunta y el profesor sabe como responder a cada uno, porque los conoce, no mezcla los conocimientos de los colaboradores, lo que si hace, es que con el contexto de la clase y del estudiante mas la pregunta piensa en la respuesta y la dice al estudiante, los demas alumnos pueden escuchar esa respuesta y pueden hacer preguntas a partir de esa pregunta/respuesta, entiendes? ese fue el ejemplo de nuestro ingeniero que nos dio”.
- The shared Room has one conversation; do not create a separate one-person Private conversation inside the Room. Preserve the existing individual AgentChatStream outside shared mode.
- User requirement: “el detalle es ver como hacer para evitar esos ecos, una solucion real, quitarlo o dejarlos tal cual no es una solucion”.
- For each public Room answer, combine diagram/room context and the current public question with only the authenticated requester's current, closed teaching profile. The AI privately evaluates that requester's interaction against their existing profile and decides whether to retain or update a reusable teaching-style preference. It must never carry another collaborator's profile or persist free-form facts or prose as personal memory.
- Room interactions and answers remain public to collaborators. A correction spoken in the Room is itself a public message; do not treat it as a private channel.
- Keep only the closed profile as active Room memory in browser IndexedDB, scoped by user and diagram. Do not read, render, or transmit legacy free-text note records; leave those old local records untouched rather than deleting user data without consent. Learn from the current requester's own Room interactions without a free-text memory note, preview/approval step, or memory-management panel. Do not show personal profiles, shared summaries, pinned decisions, or memory controls in the Room chat UI. The user may request a correction conversationally; the AI compares it to the existing profile and selects the resulting allowed values.
- The profile contract remains limited to `detailLevel` (`concise`, `balanced`, `step_by_step`) and `exampleStyle` (`uml`, `code`, `analogy`, `none`). These are intentionally shareable teaching controls that may affect the public answer. Do not store sensitive facts, free-text summaries, or arbitrary instructions.
- If an interaction has no clear reusable preference, retain the current profile unchanged. If profile learning fails, never replace it with raw text or claim that a correction was saved; fail closed for profile mutation, preserve the existing safe profile, and continue the public request using that profile when available.
- Preserve the one public Room conversation. Both typed and voice interactions update/use only the authenticated requester's closed profile; no separate personal memory text is written into prompts, history, events, rolling summary, or pinned decisions beyond the user's already-public Room message.
- The question and generated answer are public Room messages attributed to the authenticated requester/AI. Collaborators can hear the answer and follow up in the same shared conversation.
- Preserve requester identity/authorship isolation. The Room context includes the synchronized board, shared summary/pins, and public Room messages.
- Enforce the 10,000-token prompt ceiling on the final Room AI prompt using a local tokenizer configured for the exact self-hosted model. The AI service is the source of truth because it assembles the final prompt; never substitute character counts. Missing or mismatched tokenizer configuration fails closed before inference.
- Define the shared snapshot contract consumed by this builder, so #20 can provide it later without a dependency cycle.
- Target a single server instance. Use its shared-room replica only after synchronization; fail closed if the replica is unavailable or not ready. Cross-instance board synchronization is out of scope.
- Preserve link-based shared-room access for any authenticated user possessing the room link; do not require explicit invitations. Isolate unauthenticated local-mode sockets from shared-room state.

### S2 — Issue #19: Connect queued Room AI requests

- User requirement: “sera 3 pr, pero no subiremos ninguno hasta que los 3 funcionen bien”.
- Connect the existing queue to context construction, the configured model endpoint, persisted response, and room broadcast.
- Before a typed or voice interaction is queued (voice after transcription), the profile learner compares the sender's existing closed profile with only that sender's own interaction, then returns a strictly validated closed profile update through the requester-bound path. No personal free-text note is collected or transmitted. Store the resulting profile only in the sender's browser and send a one-shot sidecar containing only requester identity, validated profile, and opaque revision, with the existing maximum 15-minute TTL. Consume it once and fail closed if missing, expired, invalid, stale, or revoked.
- Profile changes rotate the corresponding revision and invalidate queued requests that carry the previous profile. Enqueue, transcription-to-enqueue, inference start, and the complete shared commit (summary update, history append, broadcast) must enforce the revision without a check-then-publish race. Acknowledged profile changes serialize with every public sink: if publication wins first, it completes before the update is acknowledged; if the update wins first, the stale answer is suppressed. Already-published messages are not retroactively deleted.
- If the browser is offline or cannot obtain the profile/revision update acknowledgement, do not overwrite the locally stored profile or send stale personalization; surface an honest message through the existing chat status/error treatment without adding a memory-management panel.
- The profile-learning endpoint uses the configured self-hosted model only, accepts a prior closed profile plus the current sender's public interaction, returns only a strict allowlisted profile, and fails closed on malformed output or unavailable configuration. Preserve the prior profile when learning fails; never persist free-text model output, use external fallback, or log the interaction body in the private-learning path.
- Use the configured self-hosted Room AI provider. Never fall back from a request carrying personal memory to an external provider.
- VM address/model settings are runtime configuration; do not hardcode GCP-specific values or expose credentials in the browser.
- Route both typed and voice-transcribed Room questions through the same public Room request path, preserving #22 behavior.

### S3 — Issue #20: Maintain shared room memory

- Keep rolling room summary and pinned team decisions shared by collaborators and scoped to their room/board.
- Updates must be bounded and safe under concurrent requests; personal memory is never stored in this shared layer.

Also verify shared-memory isolation/concurrency, token budget, and repository checks. Use deterministic stubs; real VM/model smoke requires an authorized endpoint.
